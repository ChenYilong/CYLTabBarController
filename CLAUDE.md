# CYLTabBarController — Repository Instructions

Instructions for anyone (people and AI agents) changing this repository. The library is an iOS tab bar
(Objective-C, usable from Swift) with Lottie, Liquid Glass and FlatDesign styles. See `README.md` for the API.

## 1. Documentation is part of every new feature

Every new feature (and every user-visible behavior change) ships with **bilingual Chinese–English documentation in
two places**:

1. **A document in `docs/`**: a new file named after the feature, e.g. `docs/Login-Required-Tabs.md`. It explains what
   the feature does, how to use it (Objective-C, and Swift when it differs), the API, the demo, and its limits.
2. **An update to `README.md`**: at least a feature bullet in the latest-version preview that links to the `docs/`
   file; add a full README section when the feature is part of the core usage.

### Bilingual format

- Prose is written as a two-column table: **the left column in Chinese, the right column in English**, one row per
  passage. Copy the header row from any existing table in `README.md` or `docs/` (its left header is the Chinese word
  for "Chinese", its right header is `English`):

  ```markdown
  | <Chinese header> | English |
  |:---|:---|
  | <the passage in Chinese> | The same passage in English. |
  ```

- Tables with more columns (API tables, comparisons) either carry both languages in each cell, or are given twice:
  a Chinese table followed by its English twin with the same rows.
- Headings come in pairs on consecutive lines, `## [CN]<Chinese title>` then `## [EN]<English title>`, or as a single
  heading `## <Chinese title> / <English title>`.
- Code blocks are shared between the two languages; their comments may be bilingual.
- Both columns say the same thing. Do not leave a passage in only one language.

### Screenshots and attachments

- **Debugging screenshots** that show the feature working (no bugs visible) are kept: save them in `docs/assets/` and
  embed them in the feature's `docs/` file.
- **Final screenshots** of the finished feature also go into `README.md`.
- If a change could not be run (no simulator or device), say so in the document instead of adding screenshots, and
  never present a mock-up or a diagram as a screenshot.
- **Attachment layout (Obsidian rule)**: a Markdown file's attachments live in an `assets/` folder **next to that file**,
  and are linked with the **shortest relative path**:
  - `docs/*.md` → `docs/assets/`, linked as `assets/name.png`
  - `README.md` → `assets/` at the repository root, linked as `assets/name.png`
  - No absolute paths, no `../` paths for attachments, no other attachment folders. Use lowercase, hyphenated file
    names that name the feature, e.g. `assets/login-required-tabs-alert.png`.
- Diagrams are welcome: Mermaid blocks in the Markdown, and optionally an SVG copy in `assets/`.

## 2. Navigation is generated — keep it up to date

The navigation of the documentation is generated by `scripts/update-docs-navigation.py` (Python 3, standard library
only). Everything between `<!-- navigation:start -->` and `<!-- navigation:end -->` is generated: never edit it by
hand. The script writes:

- **Page contents**: a bilingual contents table in `README.md` and in every `docs/*.md` file, one row per heading,
  linking to the Chinese and the English heading. A new document gets its contents section automatically, right
  before its first level-2 heading.
- **Documentation index**: every `docs/*.md` file with its Chinese and English title, in `README.md` and in
  `docs/README.md`.
- **Folder layout**: the tree of files and folders under `docs/` (attachments included), in `docs/README.md`.

**Run it after any change** to `README.md` or `docs/`: a Markdown edit, a heading added or renamed, or a file or
folder added, renamed, moved or removed:

```sh
python3 scripts/update-docs-navigation.py          # rewrite the navigation
python3 scripts/update-docs-navigation.py --check  # exit 1 if it is out of date
```

- AI agents run it themselves after every such change, before committing.
- The `Docs navigation` GitHub Actions workflow runs `--check` on pull requests and fails when the navigation is
  stale.
- Links: README anchors include the `[CN]` / `[EN]` prefixes. After the script runs, every in-page link it writes
  points to an existing heading; check hand-written in-page links too when you rename headings.

## 3. Every document is bound to its code classes

Each `docs/*.md` file (except the generated `docs/README.md`) is bound to the code classes it documents, and those
classes link back to it:

- **In the document**: right under its title, declare the classes on one line (or `none` for a document about no code):

  ```markdown
  <!-- bound-classes: CYLPlusButton, CYLTabBarController -->
  ```

  The script writes a bilingual table below it (between `<!-- binding:start -->` and `<!-- binding:end -->`) that
  lists each bound class with the path of its header.
- **In each bound header**: right below the copyright comment, the script writes a bilingual `[EN]` / `[CN]` comment
  between `// docs-binding:start` and `// docs-binding:end` with the GitHub link of every document bound to that class
  (`https://github.com/ChenYilong/CYLTabBarController/blob/master/docs/<name>.md`).
- **Keep it current**: whenever a document is added, renamed or removed, a declaration changes, or a class header is
  moved or renamed, run `python3 scripts/update-docs-navigation.py`. It finds every class by its
  `@interface Name :` declaration under `CYLTabBarController/`, so moved headers and renamed documents are updated
  automatically. A declared class that cannot be found, or a document without a declaration, is an error, and the
  `Docs navigation` workflow fails.
- Never edit the generated binding blocks by hand; change the declaration instead.

## 4. Code rules

- **No warnings**: fix every build and static-analyzer warning you meet, including old ones in code you did not change.
- **Public API**: never remove or change an existing public API; add new API instead. Prefer implementing an existing
  protocol method over adding a new category method; file-private C functions and private headers are fine.
- **Swift-friendly names for underscored protocol methods**: Swift method names must not contain underscores, but a
  Swift class that implements an Objective-C protocol method must use its imported name (e.g. `cyl_play…`); renaming it
  no longer satisfies the protocol. Adding `NS_SWIFT_NAME` to the existing method would change a Swift API already
  released on `master`, which the Public API rule forbids. Instead, add a new method with the same name minus the
  underscore, keeping the `cyl` prefix (e.g. `-cyl_playSelectAnimationWithTabButton:…` →
  `-cylPlaySelectAnimationWithTabButton:…`), and define its Swift name with `NS_SWIFT_NAME` on the new method only.
  Both spellings run the same logic: the library calls the underscore-free one when it is implemented, otherwise the
  underscored one. If the old method was `@required`, make it `@optional` so a class can implement only the new one.
- **Optional components are isolated with guards**:
  - FlatDesign code in Core: `#if CYL_FLATDESIGN_AVAILABLE` (defined once in `CYLUtils/CYLUtilsMacros.h`), and run only
    for `CYLTabBarStyleTypeFlatDesign`, so Liquid Glass and the classic style are never affected.
  - Lottie: separate `__has_include` guards; check keys first; call through `respondsToSelector:` and
    `cyl_performSelector`.
  - An animation library's own keys exist only with that library: its header defines `CYL_<LIBRARY>_AVAILABLE`
    (`__has_include` of the library), and the header's content and the `.m` definitions sit inside it (`CYL_PAG_AVAILABLE`,
    `CYL_RIVE_AVAILABLE`). Core and CYLUtils get no library switch. The released Lottie keys stay defined and are marked
    `CYL_LOTTIE_REQUIRED` (a compile warning without Lottie). See docs/Tab-Bar-Item-Animation.md.
- **Comments are bilingual**: write `[EN]` / `[CN]` blocks; mark fixes with `FIX: issue #N`. A comment written in
  Chinese is tagged `[CN]` and is followed directly by its English translation tagged `[EN]`, in the same comment style
  (`//`, `///`, or inside the same block comment; for a trailing comment, on the next line). Comments that only
  contain a person's name, and commented-out code, need no translation.
- **No Chinese text in code**: every string literal that contains Chinese, including log, assert and debug messages,
  goes through `CYLLocalizedString(@"<original Chinese text>")` (Swift: `CYLLocalizedString("...")`), with
  `[NSString stringWithFormat:]` / `String(format:)` for values. `CYLLocalizedString()` is declared with
  `NS_FORMAT_ARGUMENT(1)`, so keep placeholders and arguments in step. The only exceptions are resource identifiers
  (e.g. an image asset name) and constants that are documented as localization keys; never touch Xcode project
  files, plists or storyboards for this.
- **Localization tables**: every key is added to **all** `.lproj` folders in
  `CYLTabBarController/Resources/CYLTabBarController.bundle/`, keeping the same `%@` / `%1$@` specifiers; every
  table has the same keys.
- **Examples**: they import only `#import <CYLTabBarController/CYLTabBarController.h>` (Swift: `import CYLTabBarController`),
  and their Podfiles must not need changes.
- **Verify** before pushing: `pod lib lint CYLTabBarController.podspec --quick`, plus a build or static check of the
  changed code. Say plainly what could not be verified.

## 5. Xcode project files keep the ObjC example's format

**Purpose: keep CI/CD from failing.** CI and releases run on the `macos-26` runner (Xcode 26.x, no Xcode 27; see
`docs/Mac-CI-CD.md`). A project saved in a newer format cannot be opened there, and its job fails. This happened to
`scripts/ci-build-example.sh "Example-Swift-SwiftManager-FlatDesign"` after Xcode 27 saved that project
(fixed in [#772](https://github.com/ChenYilong/CYLTabBarController/pull/772)):

```
xcodebuild: error: Unable to read project 'TWDFGASDGDSFDFG.xcodeproj' from folder '/Users/runner/work/CYLTabBarController/CYLTabBarController/Example-Swift-SwiftManager-FlatDesign/.'.
	Reason: The project 'TWDFGASDGDSFDFG' cannot be opened because it is in a future Xcode project file format (110). Adjust the project format using a compatible version of Xcode to allow it to be opened by this version of Xcode.
```

**When this applies**: you create an Xcode project, or a commit touches any file inside a `*.xcodeproj` (above all
`project.pbxproj`). Before committing, search the diff for it, e.g. `git diff --cached --name-only | grep '\.xcodeproj/'`,
and check every project it lists.

**Keywords**: besides `.xcodeproj`, search the commit's code (the diff) for these keywords. A hit means an Xcode
project setting changed and this section applies. Each keyword is followed by a complete example of the line it
appears in, taken from the fix in #772 (CI/CD passed with these values), and by what to do when it shows up:

| Keyword | Complete example (#772) | Guidance |
|:---|:---|:---|
| `.xcodeproj` | `Example-Swift-SwiftManager-FlatDesign/TWDFGASDGDSFDFG.xcodeproj/project.pbxproj` | Any file under a `.xcodeproj` changed: run the check below on that project. Compare it with `CYLTabBarController.xcodeproj`; if the diff is large because Xcode rewrote the project, keep only the changes you meant and restore the format values. |
| `objectVersion` | `objectVersion = 46;` (was `110`) | Must stay `46`. If Xcode raised it, set it back. A value of 77 or more usually comes with folder sync: convert that to explicit file lists as #772 did; do not just change the number. |
| `compatibilityVersion` | `compatibilityVersion = "Xcode 3.2";` (was `"Xcode 8.0"` / `"Xcode 9.3"` / missing) | Must be `"Xcode 3.2"`, in the `PBXProject` object right after `buildConfigurationList`. Add it when missing, and remove `preferredProjectObjectVersion` and the top-level `validationLevel` if present. |
| `IPHONEOS_DEPLOYMENT_TARGET` | `IPHONEOS_DEPLOYMENT_TARGET = 15.0;` (`Example-Swift-04`, was `27.0`) | Never 27 or more, not even at the project level. Use 15.0, like the ObjC example; match the app's Podfile `platform :ios` so the app is not below its pods. Before lowering it, check the code for newer APIs without `#available`. A raised value is usually an accident of a newer Xcode saving the project (e.g. #669), not a code need. |

```sh
git diff --cached --name-only | grep '\.xcodeproj'
git diff --cached | grep -E 'objectVersion|compatibilityVersion|IPHONEOS_DEPLOYMENT_TARGET'
```

**Example fix**: [#772](https://github.com/ChenYilong/CYLTabBarController/pull/772) brought every example back to the
ObjC example's format. Follow its diff when a project needs the same fix: format 110 / 77 / 60 / 50 / 48 set to 46,
folder sync replaced by explicit file lists, the Xcode 27-only keys removed, and every deployment target of 27.0 lowered
to 15.0 (FlatDesign's project level, `Example-Swift-04`'s app target).

**The rule**: every project matches the root ObjC example, `CYLTabBarController.xcodeproj`:

- `objectVersion = 46;` in `project.pbxproj`, and `compatibilityVersion = "Xcode 3.2";` in the `PBXProject` object
  (right after `buildConfigurationList`).
- No `preferredProjectObjectVersion` key, and no top-level `validationLevel` key (Xcode 27 only).
- No folder sync: no `PBXFileSystemSynchronizedRootGroup` or `PBXFileSystemSynchronizedBuildFileExceptionSet`
  (format 77+, Xcode 16). List the files explicitly: `PBXGroup`, `PBXFileReference`, `PBXBuildFile` in the Sources /
  Resources phases, and `PBXVariantGroup` for `Base.lproj` storyboards. Keep the target membership the same (e.g.
  `Info.plist` stays out of Resources). New files are added to the target by hand in Xcode.
- No effective deployment target newer than the CI SDK: no `IPHONEOS_DEPLOYMENT_TARGET` of 27 or more, not even at the
  project level when a target overrides it.
- Scheme files (`*.xcscheme`) may keep `version="1.7"`; Xcode 15 and later read it.

**Check it** (each line must print `46` and `"Xcode 3.2"` and nothing else):

```sh
for f in $(git ls-files '*.pbxproj'); do
  echo "$f: $(grep -oE 'objectVersion = [0-9]+|compatibilityVersion = "[^"]+"|preferredProjectObjectVersion|validationLevel|PBXFileSystemSynchronized[A-Za-z]*|IPHONEOS_DEPLOYMENT_TARGET = (2[7-9]|[3-9][0-9])' "$f" | sort -u | tr '\n' ' ')"
done
```

- When Xcode upgrades a project's format (it does when a newer Xcode saves it), set those values back before committing.
- A project that uses folder sync has to be converted to explicit file lists, not just relabeled. Afterwards check it
  with CocoaPods' parser (`ruby -rxcodeproj -e 'Xcodeproj::Project.open(ARGV[0])' <path>.xcodeproj`, run with
  `LC_ALL=C.UTF-8`) and make sure every file in its build phases exists on disk.
- Say in the PR that the project was not opened in Xcode when it could not be; the `Demo …` CI jobs on `macos-26` are
  the real check.

## 6. Git and pull requests

- Branch from the latest `master` for each issue or feature.
- Commit messages are in English, Conventional Commits as configured for commitizen in `package.json`
  (`feat: ✨ …`, `fix: 🐛 …`, `docs: 📝 …`).
- Push early and open the pull request once the change is substantial; the PR body closes the issue (`Closes #N`).
- Before merging, squash the PR into a single commit and push with `--force-with-lease` (never a plain force push).
  On someone else's branch, merge `master` in instead of rebasing.
- After opening the PR, comment on the issue (in the issue's language) with the changes, the commit link, and an
  invitation to try the latest version.
