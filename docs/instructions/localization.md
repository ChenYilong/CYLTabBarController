# Localization File Structure [`localization`]

Localized texts are always many files, one per language: they are never left as loose `.lproj` folders in a target or folder, but grouped and reached through one entry point.

## iOS: one `.bundle` per owner

Put all the `.lproj` folders of a set of tables into one `.bundle` (`<Name>.bundle/<language>.lproj/<Table>.strings`). Several bundles are fine, one per owner or purpose.

## The core bundle is permanent

`CYLTabBarController/Resources/CYLTabBarController.bundle` (table `CYLTabBarController`) ships with the library: always keep it, with its name, path, and table name, and update it carefully. It holds the library's own texts only. Every key goes into **all** its `.lproj` folders with the same `%@` / `%1$@` specifiers, so every table has the same keys; never rename or remove a key that released code reads; check for duplicate keys with `LC_ALL=C sort`.

## Examples have their own bundle

Texts that only an example shows go into a bundle that belongs to the example (in its own folder, or in `Example-Shared/` when several examples share it), not into the core bundle. Xcode's `Base.lproj` for storyboards and launch screens stays where Xcode puts it.

## Always a macro per bundle

Each bundle gets one macro (and a Swift function named in Swift style, lowerCamelCase: `cylDemoLocalizedString` for `CYLDemoLocalizedString`, as SonarCloud rule swift:S100 requires) that maps a key to its bundle and table, so callers never spell the bundle out: the core one is `CYLLocalizedString(@"…")`; an example's is, for instance, `CYLDemoLocalizedString(@"…")` over `NSLocalizedStringFromTableInBundle`. Declare it with `NS_FORMAT_ARGUMENT(1)` and `CYL_RETURNS_LOCALIZED_STRING`, like the core one.

## Acceptance criterion: at least two different macros, one per layer

A project passes only when it has at least two different macros (and their Swift-style Swift functions) that read the localized files of two different layers:

1. A **core** macro that reads the localized files inside the library's own bundle.
2. An **example** macro that reads the localized files at the example level.

On iOS these are `CYLLocalizedString` → `CYLTabBarController.bundle` and `CYLDemoLocalizedString` → `Example-Shared/CYLDemo.bundle`. Other platforms use a different package form, name, and folder name (Android `res/values*/` per module, a table file per example for React Native and Flutter), but each layer is still a folder or package of per-language files reached through its own macro or helper.

It fails when one macro reads both layers, when an example reads the core bundle through `NSLocalizedString` or `NSBundle` calls of its own, when an example's texts sit in the core bundle, or when loose `.lproj` folders are left in a target. An example project that compiles a file calling the example macro must also compile the macro's source (`CYLDemoLocalization.m` / `.swift`) and ship `CYLDemo.bundle`.

Run `python3 scripts/check-localization-macros.py` for the iOS side; it exits 1 and names each failure.

## Other platforms

Use the same structure on other platforms. Android: the library's strings in the library module's `res/values*/` (the core tables: kept, updated carefully, generated from the iOS tables by `scripts/android-library-strings.py`), an example's strings in its own module's `res/values*/`, each reached through one helper (`CYLLocalization.string` for the library, an example helper for an example). React Native and Flutter: one table file per example (`strings.json`, generated by `scripts/sync-example-shared.py`) behind one function (`t()`).
